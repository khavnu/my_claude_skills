- **No Robolectric in this project → never call real `android.graphics.Bitmap.*` from a ViewModel.**
  `:app` unit tests are plain JUnit (no Robolectric; confirmed via `grep -rn robolectric app/build.gradle.kts gradle/libs.versions.toml` → no hits). A VM that calls `Bitmap.createBitmap(...)` directly crashes every unit test that reaches it with `RuntimeException` at `Bitmap.java:-1` ("not mocked" Android stub) — even though the module compiles fine, since `compileDebugUnitTestKotlin` doesn't execute code. Fix: put the one real Bitmap call behind an injectable `fun interface` seam (see `PreviewBitmapFactory` in `app/src/main/java/com/wife/recommend/music/feature/theme/edit/EditBackgroundViewModel.kt`, bound in `app/src/main/java/com/wife/recommend/music/di/AppModule.kt` next to the existing `CurrentHour` pattern), then fake it in tests with `mockk(relaxed = true)` — no `mockkStatic`, no Robolectric needed. `BitmapThemeImageProcessor`'s own Bitmap-heavy code is why it lives in `data/src/androidTest`, not `data/src/test` — same reasoning, already established in this codebase before this fix.

- **`androidx.exifinterface:exifinterface` (NOT `android.media.ExifInterface`) has `isFlipped()`/`getRotationDegrees()` covering all 8 EXIF orientations.** Verified by decompiling `exifinterface-1.4.2-sources.jar` (`androidx/exifinterface/media/ExifInterface.java` around line 4716-4758): `isFlipped()` is true for exactly orientations 2/4/5/7 (`FLIP_HORIZONTAL`, `TRANSVERSE`, `FLIP_VERTICAL`, `TRANSPOSE`); `getRotationDegrees()`'s own kdoc states the image is "first flipped horizontally, then rotated" — so flip always composes BEFORE rotation. The framework `android.media.ExifInterface` has no flip-aware API at all (only `TAG_ORIENTATION` raw int). To invert a flip+rotate crop-rect mapping: compute the existing rotation-only rect, then if `isFlipped`, mirror left/right only (`newLeft = 1 - oldRight, newRight = 1 - oldLeft`) — see `BakeGeometry.toStoredRect` in `data/src/main/kotlin/com/wife/recommend/music/data/theme/imaging/BakeGeometry.kt`. For the pixel draw, apply the mirror via `Matrix.preScale(-1f, 1f)` called right after `setRotate(...)` (pre-concat runs before the already-set rotation) — see `BitmapThemeImageProcessor.drawScaled`.

- **`runTest` reuses `Dispatchers.Main`'s scheduler when it's already a `TestDispatcher`** (set by `MainDispatcherRule` before `runTest` starts) — so a VM constructor arg of type `CoroutineDispatcher` can safely be satisfied in tests with `mainDispatcherRule.dispatcher` (the exact same instance Main uses), keeping `advanceTimeBy` in sync with `withContext(thatDispatcher) { ... }` calls inside the VM. Used for `EditBackgroundViewModel`'s injected `@DefaultDispatcher` param.

- **`ColumnScope.weight(1f, fill = false)` + `Modifier.aspectRatio(...)` on the SAME node, inside a plain (non-scrolling) `Column`, auto-shrinks to fit leftover space** — Compose's aspectRatio modifier falls back from width-based to height-based sizing when the width-based height would exceed the given `maxHeight` (verified against `RowColumnMeasurePolicy.kt` from `foundation-layout-android-1.12.0-sources.jar`: non-weighted/weighted children are measured with a bounded `mainAxisMax` whenever the Column itself isn't inside a scrollable ancestor). This is what fixed WMusi's Edit-background screen overflow (`app/src/main/java/com/wife/recommend/music/feature/theme/edit/EditBackgroundScreen.kt`) without needing `verticalScroll` on the same node as the weighted child — combining `verticalScroll` directly with a `weight`-using sibling on the identical Column does NOT crash (confirmed from the same source: it falls back to `mainAxisMin`, typically 0) but silently collapses the weighted child to ~0 height, so don't do it; nest the scroll in a child Column instead if a scroll fallback is ever needed.
